# Мастер-интеграция: внешняя система управляет Chatick через API

ТЗ на интеграцию с внешними системами уровня компании — когда у заказчика уже
есть своя платформа (проекты, гант, финансы, воронка, статистика), и он хочет
перенести к нам **задачи, время, чат, файлы и документы**, не отказываясь от
своей аналитики.

> **Ничего из этого пока не написано.** Документ — план, а не отчёт.

---

## 1. Кто главный

Разделение ответственности, от которого пляшет всё остальное:

| Живёт у них | Живёт у нас |
|---|---|
| Проекты (создание, сроки, команда) | Задачи и чек-листы |
| Клиенты, воронка, финансы | Учёт времени |
| Статистика и отчётность | Чат и ИИ-диспетчер |
| Пользователи (источник истины) | Файлы, документы, заметки |

**Проекты и люди приходят снаружи.** Мы их не выдумываем — мы их принимаем,
храним связь с внешним идентификатором и отдаём обратно всё, что вокруг них
наросло.

**Задачи наружу не импортируются.** Их можно читать через API для статистики,
но заливать чужие задачи к нам мы не будем: формат другой, редактор другой, и
смешение форматов испортит и то и другое.

---

## 2. Ключи доступа

Сейчас `api_tokens` привязаны к человеку. Для интеграции нужен ключ **уровня
компании** — он переживает увольнение того, кто его завёл.

### Таблица `company_api_keys`

| Поле | Смысл |
|---|---|
| `companyId` | чей ключ |
| `name` | «Atlas, продакшн» — чтобы отличать при отзыве |
| `keyHash` | сам ключ не хранится, только хеш |
| `prefix` | первые 8 знаков — показать в списке, не раскрывая ключ |
| `scopes` | что разрешено: `users:write`, `projects:write`, `read:all` |
| `createdById`, `lastUsedAt`, `revokedAt` | кто завёл, когда пользовались, когда отозвали |

**В интерфейсе Chatick:** раздел компании → «Интеграции». Создать ключ,
посмотреть список с датой последнего использования, отозвать.

**Ключ показывается один раз** — при создании. Дальше только префикс. Потеряли
— выпускайте новый, старый отзывайте.

**Отзыв мгновенный:** `revokedAt` проверяется на каждом запросе, а не по
истечении срока.

### Как передаётся

```
Authorization: Bearer ck_live_xxxxxxxxxxxxxxxxxxxx
```

Ограничения на каждом ключе:
- частота запросов (иначе один сорвавшийся цикл на их стороне положит нам API);
- список IP, с которых ключ принимается — необязательный, но для продакшна
  стоит включать.

## 3. Пользователи

### Первый запуск: перенос существующих

Скрипт на нашей стороне тянет их список через **их** API и заводит людей у нас.
Разово, вручную, с отчётом «создано / уже было / не удалось».

### Дальше: они добавляют, мы принимаем

```
POST /api/v1/ext/users            один
POST /api/v1/ext/users/batch      пачкой, до 500 за раз
```

```json
{
  "externalId": "atlas-4821",
  "email": "dev@company.com",
  "name": "Ido Winegarten",
  "companyRole": "member",
  "projects": [
    { "externalProjectId": "atlas-p-77", "role": "member",
      "permissions": { "tasks": "crud", "files": "write", "documents": "write" } }
  ],
  "notify": true
}
```

**Без подтверждения.** Человек оказывается в компании и проектах сразу — это и
просили. Письмо уходит **постфактум**: «вас добавили в проект», со ссылкой.
Одобрять ничего не нужно.

> Это осознанное послабление, и оно допустимо ровно потому, что список людей
> ведёт сама компания в своей системе. Ключ, позволяющий такое, — по сути
> ключ от всей компании. Отсюда требования из раздела 2: отзыв, ограничение
> по IP, журнал.

**Повторный вызов не плодит дублей:** ключ поиска — `externalId`, затем email.
Существующему обновляем роль и доступы.

### Уход человека

```
DELETE /api/v1/ext/users/:externalId          из компании
DELETE /api/v1/ext/users/:externalId/projects/:externalProjectId
```

Данные человека остаются (сообщения, задачи) — уходит доступ.

## 4. Проекты

```
POST   /api/v1/ext/projects
PATCH  /api/v1/ext/projects/:externalProjectId
GET    /api/v1/ext/projects
DELETE /api/v1/ext/projects/:externalProjectId    только архивирование
```

```json
{
  "externalId": "atlas-p-77",
  "name": "Мобильное приложение",
  "externalName": "אלירן בוכמן ורותם חיים",
  "externalUrl": "https://atlas.company.com/projects/77",
  "members": [{ "externalUserId": "atlas-4821", "role": "admin" }]
}
```

### Двойное имя

Заказчик зовёт проект по имени клиента, мы — по сути работы. Оба нужны:

```
Мобильное приложение   ·   אלירן בוכמן ורותם חיים
      наше имя                  их имя, рядом, приглушённо
```

Хранится в `projects.externalName`, показывается везде, где показывается
название.

### Запрет создания из интерфейса

Настройка компании: **проекты создаются только через API**. Кнопка «Новый
проект» исчезает у всех, включая владельца. Иначе появятся проекты, которых
нет в их системе, и синхронизация посыпется.

## 5. Переходы между системами

**Из их системы к нам.** Ссылку не собирают вручную — просят у API:

```
POST /api/v1/ext/projects/:externalProjectId/link
→ { "url": "https://app.chatick.com/#/go/eyJhbGci...", "expiresInSec": 300 }
```

Одноразовая ссылка живёт пять минут: человек уже вошёл в их систему, мы
доверяем ключу компании и пускаем его в проект без второго входа.

**От нас к ним.** В шапке проекта — кнопка с их логотипом, ведёт на
`externalUrl`. Настраивается один раз на компанию:

```json
{ "externalSystemName": "Atlas", "externalProjectUrlTemplate": "https://atlas.company.com/projects/{externalId}" }
```

Так это остаётся **универсальным**: ничего специфичного для одного заказчика в
коде нет — только шаблон ссылки и название системы.

---

## 6. Что можно прочитать

Всё, что относится к их компании — для их статистики:

```
GET /api/v1/ext/projects/:id/tasks          задачи со статусами и оценками
GET /api/v1/ext/projects/:id/time           часы: кто, когда, сколько, по какой задаче
GET /api/v1/ext/projects/:id/activity       журнал изменений
GET /api/v1/ext/stats/summary               сводка по компании
GET /api/v1/ext/users/:externalId/time      часы одного человека
```

Ответы постраничные, с курсором. Фильтры по датам — чтобы забирать только
новое, а не всю историю каждый раз.

**Чего наружу не отдаём:**
- содержимое чата — это переписка людей, а не отчётность;
- значения секретов — никогда и никому;
- личные ИИ-диалоги.

Задачи и часы — да, потому что ради этого всё и затевается.

## 7. Уведомления к ним (позже)

Чтобы их статистика не ждала опроса, а обновлялась сразу:

```json
POST <их webhook>
{ "event": "task.status_changed", "projectExternalId": "atlas-p-77",
  "taskNumber": "TASK-42", "status": "done", "at": "..." }
```

Подпись `HMAC-SHA256` заголовком `X-Chatick-Signature` — чтобы они могли
убедиться, что запрос от нас. Повторы при сбое с нарастающей паузой.

Не в первой версии, но структура должна это допускать.

---

## 8. Вход через их систему

Отдельная задача, коротко:

- человек вводит почту у нас;
- мы спрашиваем их API: есть такой? к каким проектам допущен?
- пускаем, права берём оттуда.

**Важно:** это не должно стать полной зависимостью. Если их система недоступна,
**уже вошедшие продолжают работать** — сессия наша, проверка их нужна только на
входе и при обновлении списка проектов.

---

## 9. Безопасность

- Ключ компании даёт много — поэтому отзыв, ограничение по IP, ограничение
  частоты и **журнал каждого вызова** (кто, что, когда, с какого адреса).
- Все внешние ручки под `/api/v1/ext/*` — отдельный префикс, отдельная
  проверка, ничего общего с сессиями людей.
- Ключ виден один раз при создании.
- Внешняя система **не может**: удалять проекты насовсем (только архив),
  читать секреты, читать переписку.
- Каждое действие извне попадает в журнал проекта как «через интеграцию», а не
  безымянно.

## 10. Порядок работы

| Шаг | Что | Зачем сначала |
|---|---|---|
| 1 | Ключи компании: таблица, интерфейс, проверка | без этого нельзя вызвать ничего |
| 2 | Проекты: создание, обновление, двойное имя, запрет создания в UI | на них вешаются люди |
| 3 | Пользователи: поштучно и пачкой, без подтверждения, письмо постфактум | наполнение |
| 4 | Чтение: задачи, часы, журнал, сводка | их статистика |
| 5 | Переходы: ссылка к нам, кнопка к ним | связность |
| 6 | Скрипт первичного переноса людей | разовый запуск |
| 7 | Вебхуки | когда опроса станет мало |
| 8 | Вход через их систему | отдельно, после остального |

Каждый шаг заканчивается работающей ручкой и записью в справке моста — иначе
внешняя команда не сможет ей воспользоваться.
