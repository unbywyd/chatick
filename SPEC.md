# Chatick — техническое задание (живой документ)

> Концепция: [CONCEPT.md](./CONCEPT.md). Здесь — детальные требования по мере поступления.
> Обновлено: 2026-07-23.

---

## 1. Иерархия сущностей

```
Компания (Company/Team)
├── участники компании (системные роли: Admin / Manager / Member)
└── Проекты (Project = группа = чат)
    └── участники проекта (роли проекта: owner / admin / member)
```

- Компания — вне проектов, содержит множество проектов.
- Компания: **название, лого**, участники.
- Проект принадлежит компании.

## 2. Роли и пермишены

### 2.1 Системные роли компании

| Роль | Права (базовая матрица, конфигурируемая) |
|---|---|
| **Admin** | всё: настройки компании, роли, инвайты, создание/удаление проектов |
| **Manager** | создавать проекты, приглашать в проекты, приглашать в компанию |
| **Member** | участвовать в проектах, куда добавлен |

- Права заданы **логическими пермишенами** (флаги: `canCreateProjects`, `canInviteToCompany`, `canManageMembers`, …), роль = преднастроенный набор флагов. Матрица настраивается на уровне компании.
- Создавать проекты может Admin или Manager (по умолчанию).

### 2.2 Роли проекта

- owner / admin / member (как заложено в схеме).
- На уровне проекта — свои пермишены (кто может приглашать в проект, менять правила ИИ, управлять задачами и т.п.).

## 3. Приглашения

### 3.1 В компанию — с подтверждением

- Приглашение **по email** с указанием роли.
- Флоу: инвайт создан → письмо со ссылкой-токеном → приглашённый подтверждает → становится участником.
- Управление инвайтами: **переслать** (повторное письмо), **удалить/отозвать**, список pending-инвайтов.
- Если у приглашённого нет аккаунта — после Google-логина инвайт подхватывается по email.

### 3.2 В проект — без подтверждения

- Участника компании просто **включают** в проект (никакого accept-флоу).
- Постфактум отправляются письма: **«вас добавили в проект»**, **«вас убрали из проекта»**.

## 4. Правила проекта и конфигурация ИИ

Детальная страница настроек ИИ у каждого проекта.

### 4.1 Конфигурация ИИ-диспетчера (пересмотрено 2026-07-23)

Принцип: каждый параметр мапится в конкретное **действие** диспетчера, никаких абстрактных процентов.

```
aiConfig:
  mode: observer | assistant | moderator      — режим вмешательства (3 карточки)
    observer  — только перевод + ответы при прямом обращении к ИИ
    assistant — + сам отвечает на вопросы из контекста, предлагает действия (default)
    moderator — + придерживает: непонятное (уточнить), дубли (ссылка), оффтоп
  language: код языка                          — ЯЗЫК ПРОЕКТА (канонический язык чата)
  autoTranslate: bool                          — переводить сообщения на язык читателя (default on)
  answerRepeats: bool                          — дедуп: отвечать на повторные вопросы за людей (default on)
  offtopic: ignore | remind | hold             — что делать с оффтопом (default remind)
```

- «Шутки/флуд/тон» — НЕ конфиг, а текстовые правила чата (§4.2).
- Управление задачами через чат — НЕ здесь, а через пермишены участника (§4.3): ИИ выполняет
  действия с задачами только в пределах прав автора сообщения.

### 4.3 Пермишены участника проекта (задачи)

Per-user галочки на уровне участника проекта (страница «Права» в проекте):

```
permissions:
  tasks.read          — всегда true (не отключается)
  tasks.create        — создавать задачи
  tasks.edit          — редактировать задачи
  tasks.delete        — удалять задачи
  tasks.changeStatus  — менять статусы
```

- Дефолты по роли: owner/admin — всё; member — read + changeStatus.
- UI: страница с чекбоксами по каждому участнику (владелец/админ проекта редактирует).
- **Синхронизировано с чатом**: ИИ-диспетчер проверяет права автора перед действием
  («создай таску» от юзера без tasks.create → вежливый отказ).
- Расширяемо на другие домены (files.*, credentials.*) тем же механизмом.

### 4.2 Текстовые правила чата (chat rules)

- Свободное текстовое поле, описывающее правила проекта.
- **Жёсткий лимит длины — буквально пара предложений** (~300 символов): текст включается в **каждый запрос ИИ** как system-контекст, длина критична для стоимости и качества.
- Показывается каждому участнику **перед вступлением** в проект и **подтверждается** им (фиксируем факт подтверждения).
- Используется в промпте ИИ-диспетчера как правила чата.

## 5. Флоу входа (утверждено)

1. Лендинг chatick.com (Astro, en/ru/he, RTL, автодетект; пока под basic-auth) → «Начать» → app.chatick.com
2. Google OAuth → **session JWT** (личность)
3. После первого логина: **создание компании** (или принятие инвайта)
4. Выбор проекта / создание нового → обмен session на **project JWT** (личность + projectId + роль)
5. Рабочий экран (чат 40% / табы 60%)
6. Таб «О проекте» + кнопка «Сменить проект» → назад к выбору (сессия жива, без релогина в Google)

## 5.5 Пайплайн ИИ-диспетчера и Sandbox (утверждено 2026-07-23)

Отправка сообщения в группу:

1. POST → статус `pending`. Остальные видят «<Имя> пишет…», автор — «проверяется…».
   Сообщение НЕ появляется в чате ни у кого до вердикта (без скачков).
2. ИИ-диспетчер оценивает (правила чата §4.2, aiConfig §4.1, контекст переписки):
   - **PASS** → `delivered`, появляется у всех одновременно (вкл. автора).
   - **HOLD** → `held`, у автора открывается **Sandbox-оверлей**.
3. **Sandbox** — приватный временный канал автора с ИИ (никто другой его не видит):
   - исходное сообщение + замечания/вопросы ИИ;
   - диалог с ИИ до готовности; ИИ предлагает варианты сообщения;
   - годные варианты помечены ✓ и кнопкой **«Выбрать»** → уходит в общий чат, sandbox закрывается;
   - кнопка «Посмотреть чат» — подглядеть общий чат, не теряя sandbox;
   - «Отменить» — отбросить сообщение целиком;
   - обход: режим **assistant** — есть «Отправить как есть»; **moderator** — только одобренные ИИ варианты.
4. **Вложения**: файлы/картинки прикрепляются к сообщению в композере; при HOLD остаются
   привязанными и отправляются вместе с выбранным финальным вариантом.

## 5.6 Память ИИ: сжатие переписки и инструменты (утверждено 2026-07-23)

Беседы бесконечны, контекст LLM конечен, терять информацию нельзя. Трёхслойная память:

1. **Живой хвост** — последние ~30 сообщений сырыми в каждом промпте.
2. **Саммари-цепочка** — переписка нарезается на «беседы»: при накоплении >60 несжатых
   сообщений старшие 40 сжимаются ИИ в саммари с ИИ-сгенерированным **именем**
   (короткое, «о чём была беседа»), датами from/to и messageCount. Курсор —
   projects.lastSummarizedAt. В промпт идёт ОГЛАВЛЕНИЕ (список имён+дат) + последнее
   саммари целиком. Сырые сообщения не удаляются.
3. **Инструменты** — ИИ сам достаёт остальное (tool-use цикл, до 5 итераций):
   - list_summaries(page) — список бесед: имя, даты, счётчик; пагинация
   - get_summary(id) — полный текст саммари
   - search_messages(query) — поиск по сырой истории (полнота гарантирована)
   - list_files(query?) — файлы проекта (имена+ссылки), list_tasks / get_task
   - create_task / update_task / delete_task / change_task_status — CRUD задач
     **с проверкой пермишенов автора сообщения** (§4.3): нет права — вежливый отказ.

Промпт любого вызова (диспетчер, sandbox, ответы) = system + оглавление + последнее
саммари + живой хвост + tools. ИИ «видит» всю историю: свежее напрямую, старое —
через оглавление и инструменты.

## 7. Лимиты и подписки (2026-07-23)

Иерархия: лимиты живут на **компании** (уровень подписки), проекты наследуют.

- **companies**: `storageLimit` (общий пул хранилища на все проекты), `maxProjects`,
  `maxMembers`, `plan` (ярлык тарифа). Настраиваются **через БД** — задел под будущий
  биллинг (подписка = UPDATE компании).
- **projects.storageLimit**: NULL = наследует пул компании; число = override-потолок проекта.
- **Эффективный лимит проекта** = `min(override проекта, used + свободное в пуле компании)`.
  Загрузка проверяет его; 0/NULL на обоих уровнях = без лимита.
- Дефолты: компания 5 GB, проект — наследует. maxProjects/maxMembers = 0 (без лимита) до
  внедрения подписок.

## 8. Ресурсы, задачи, ИИ-CRUD, пермишены (ТЗ 2026-07-24)

Общая идея: **Ресурсы, Файлы, Задачи** — три сущности проекта. Каждой можно управлять
руками (CRUD) и через чат (ИИ пополняет их). ИИ ничего не публикует в группу, если это
логичнее оформить как задачу/комментарий/ресурс. Весь CRUD — **строго по пермишенам юзера**.

### 8.1 Ресурсы (переименование Кредишенов)

- «Кредишены» → **«Ресурсы»** (в меню/навигации).
- **Ресурс = опциональная ссылка + описание** + под ним опционально **секреты (пароли)**.
  Всё опционально: ресурс может быть только ссылкой, только секретом, или всем сразу.
- Единая логика с файлами: руками добавляем, а ИИ из чата ловит расшаренные ссылки/креды
  и **сам сохраняет в Ресурсы** с описанием, с пометкой «из чата» + связь на сообщение.
- Секреты шифруются (AES-256-GCM, как сейчас), аудит доступа сохраняется.
- Ресурсы **перетаскиваются в чат** как пин (ярлык-связь, открывает ресурс) — как задачи/файлы.

### 8.2 История чата (саммари по дням)

- В чате **убрать поиск по ссылкам/файлам** (это в Ресурсах/Файлах). В поиске оставить:
  текст + **История**.
- **История** = сжатые саммари бесед. Собирать **по дням** (с учётом размера токенов —
  если день большой, несколько саммари за день). Каждое: заголовок + текст саммари + даты.
- Всё **на языке проекта** (заголовок и содержание).
- Двойное назначение: (1) экономия контекста ИИ (ИИ читает саммари + ищет между ними
  инструментом), (2) человек вручную заходит в Историю и смотрит саммари за дату/период.
- UI Истории: список по датам, фильтр «между датами / за дату», раскрытие саммари.

### 8.3 Файлы: 3-й источник (задачи) + сохранение связи при удалении

- Источники файла: чат / задача / загруженный. **Связь никогда не теряется по-тихому.**
- Удалили файл из менеджера → там где он был (чат/задача) остаётся **«Файл удалён»**
  (soft-delete, связь сохраняется). Уже сделано для чата — распространить на задачи.

### 8.4 Задачи

- **ИИ-валидация в форме**: кнопка «Проверить мою задачу» → ИИ получает заполненное,
  предлагает улучшение, юзер может применить/поправить. Прямо в форме создания/редактирования.
- **Группировка задач** (спринты): группа с названием и цветом.
- **Табличный вид** (библиотека с вложенными таблицами: группа + задачи):
  колонки — исполнитель, краткое описание, статус (цвет), приоритет (флажок-цвет);
  сортировка по столбцам, фильтры, инлайн-смена статуса/исполнителя, **drag** (внутри
  группы, между группами, сами группы).
- **Комментарии в задачах**: с возможностью прикрепить/залить файл (файл привязан к задаче,
  в комментарии — ссылка, попадает в секцию «Файлы» задачи). **Ответы на комментарии.**
- ИИ пишет комментарии к задачам **от лица пользователя** (отвечать/писать), с файлами.

### 8.5 ИИ-инструменты (расширение)

ИИ умеет полный CRUD: задачи, комментарии, файлы, ресурсы + чтение. Сценарий: юзер выделяет
задачу/прикрепляет файл/пишет в чат → ИИ **не шлёт в группу**, а предлагает создать задачу
(с файлами) или добавить комментарий. **Всё по пермишенам автора.**

### 8.6 Пермишены пользователя (расширение §4.3)

Секция «Права» под пользователем, разбита на домены: **Файлы / Ресурсы / Задачи**.
В каждом уровни: **чтение / чтение-запись / полный CRUD** (или гранулярные галочки).
ИИ-CRUD и ручной CRUD одинаково проверяют эти права.

### 8.7 Ширина страниц (UI)

Табы в аутлете (`mx-auto max-w-3xl`) — узкие. Расширить контентную зону всех страниц
слота, чтобы занимали доступное пространство (особенно Задачи-таблица). ✅

### 8.8 Rich-text (Tiptap) везде

- **Описание задачи**: textarea → Tiptap с полным полезным набором инструментов
  (заголовки, списки, чек-листы, код, цитаты, ссылки) + **mentions команды**.
- **Комментарии задач**: минимальный Tiptap + mentions.
- Единый компонент RichEditor (пресеты: full / minimal), сериализация в markdown.

### 8.9 Уведомления и подписки

- **Email-уведомления** при: упоминании (@mention) в чате / задаче / комментарии;
  назначении задачи на человека; (расширяемо: смена статуса своей задачи, ответ на
  комментарий, добавление в проект — уже есть).
- **Страница «Уведомления»** (настройки подписки): юзер включает/выключает каждый тип
  события. Дефолты разумные (упоминания и назначения — вкл).
- Схема: `notification_prefs` (per-user, per-project или глобально) + движок отправки,
  который проверяет подписку перед письмом. Антиспам: не слать самому себе, дедуп.
- **Напоминания об открытых задачах** (per-project, настраивают admin/доступ):
  таймер (каждые N часов / раз в день в HH:MM / выбор дней) → email со списком задач
  в статусе TODO (и/или без прогресса). Реализация: cron-планировщик на сервере +
  таблица `task_reminders` (project, интервал/время, кому слать: всем участникам /
  ассайни / выбранным). Отдельная настройка на странице проекта.
  **Антиспам: минимальный интервал — не чаще раза в полдвня (everyHours ≥ 12),
  валидируется и на клиенте, и на сервере.**

## §8.10 Настраиваемое хранилище (S3/R2) — per-project

- **Секция «Хранилище» в настройках проекта** + рядом с прогресс-баром в Файлах.
- Enum источника: `platform` (наш, 1 ГБ бесплатно, дефолт) | `custom` (свой S3/R2 — без лимита).
- Для custom: endpoint, region, bucket, accessKeyId, secretAccessKey, publicUrl.
  **Ключи шифруются (AES-256-GCM), в ответах API — только метаданные/маскировка,
  секреты никогда не отдаются и не попадают в контекст ИИ.**
- Прогресс-бар лимита показываем только для `platform`; для `custom` — «без лимита».
- Загрузка/отдача файлов маршрутизируется на активный источник проекта.

## §8.11 Настраиваемый ИИ-агент + учёт использования — per-project

- **Секция «ИИ» в настройках проекта**. Enum: `trial` (наш пробный, дефолт) | `custom` (свой).
  - `trial`: наш ключ (внутри — DeepSeek, **об этом провайдере в UI не пишем** — просто
    «Пробный бесплатный»). Лимит бюджета **$2 на проект**; считаем расходы по токенам.
    Прогресс-бар 0→100% использования бюджета. На 100% — только `custom` (свой агент).
  - `custom`: свои baseUrl/apiKey/model (ключи шифруются, не утекают, не в контекст ИИ).
- **Страница логов использования ИИ** (per-project): по каждому вызову — модель,
  токены (in/out), кол-во, стоимость. Итоги и разбивка.
- **Прайсинг моделей**: маппинг известных моделей → цены (in/out за 1M токенов),
  наследуется по умолчанию. Опция задать свою цену in/out (переопределяет наследование).
  Для неизвестной модели цену не показываем, пока пользователь не задаст.
  Всё гибко и прозрачно: видно сколько потрачено и по какой цене.
- Схема: `ai_usage_log` (project, model, tokensIn, tokensOut, costIn, costOut, createdAt) +
  `model_pricing` (глобальный дефолт + per-project override) + бюджет в конфиге проекта.

## §8.12 Должность и зона ответственности участника

- У каждого участника проекта — два коротких поля: **должность** (jobTitle) и
  **за что отвечает** (responsibility). Короткий текст (лимит ~200 симв.).
- Редактируются в табе «Команда» (рядом с правами), owner/admin.
- **Опрокидываются в контекст ИИ**: диспетчер и ассистент знают, кто за что
  отвечает — чтобы адресовать задачи/вопросы правильному человеку.

## §8.13 Оценка времени задачи

- Поле **оценка времени** (в минутах, хранится числом; в UI — м/ч).
- Отображается снаружи (в списке/таблице) + инлайн-редактирование.

## §8.14 Заметки ИИ к задаче (факты / проблемы / рекомендации / опровержения)

- Секция «Заметки ИИ» в задаче: разнотипные заметки с иконкой и цветом —
  `fact` (факт, известный ИИ), `issue` (проблема), `recommendation` (рекомендация),
  `rebuttal` (опровержение/невыполнимость). Тело — markdown, рендерим в HTML.
- Конфиг чата ИИ: флаг **`generateTaskNotes`**. Если включён — при создании задачи
  ИИ получает задачу и генерирует заметки **только при реальной необходимости**
  (люди упрощают/усложняют/просят невозможное — ИИ уточняет и помогает). Может
  вернуть пусто.
- Заметки создаются автоматически (source=ai) и хранятся отдельно от описания.

## §8.15 Прогресс и фильтры на странице задач

- **Прогресс-бар реализации**: доля `done` от всех задач = 100%. Считается
  **относительно активных фильтров** (напр. «только мои» → прогресс по моим;
  сброс фильтра → снова по всем).
- Удобные фильтры + кнопка **сбросить все**. Проверить/довести: поиск по задачам,
  фильтр по типу (приоритет), по статусу, по пользователю (ассайни).

## §8.16 Поддержка буфера обмена (paste) везде, где есть загрузчик

- В чате при копировании в буфер показывать плейсхолдер «Вставить из буфера»:
  картинки → превью картинки; текст → превью пары строк с «…». Можно запинить/послать.
- Загрузчики файлов (файл-менеджер, вложения задач/комментариев — везде) должны
  поддерживать **вставку из буфера** (Ctrl+V картинки/файла → загрузка).

## §8.17 Временные вложения композера

- Файл, загруженный в композер (чат/комментарий) до отправки, помечается
  **временным** (`pendingUntil = now + 24ч`), НЕ виден в файл-менеджере.
- При отправке сообщения/комментария (привязка `messageId`/`commentId`) флаг
  снимается — файл становится постоянным.
- Cron-планировщик периодически удаляет просроченные временные файлы
  (`pendingUntil < now`, всё ещё без привязки) вместе с объектами в хранилище.

## §8.18 Реал-тайм задач и блокировка редактирования

- Доска задач обновляется по WebSocket (`tasks_changed`, `task_comments_changed`):
  изменения от ИИ или другого участника видны сразу, без перезагрузки.
- **Безопасное редактирование**: пока один участник держит форму задачи открытой,
  задача заблокирована для остальных (эфемерный лок в памяти сервера, авто-снятие
  при закрытии/дисконнекте, TTL + heartbeat). У остальных кнопка «Редактировать»
  недоступна и показывается «Правит {имя}» с аватаркой.

## §8.19 Меню профиля в шапке

- Аватар пользователя в шапке проекта → меню: смена фото (загрузка, webp 256×256,
  раздача через `/api/v1/auth/avatar/:id`) и имени (инлайн), пункты «Уведомления»
  (всем) и «ИИ и расходы» (только owner/admin) — вынесены из таб-бара, «Выход» с
  подтверждением. Единый `<Avatar>` (фото или инициал-плейсхолдер) используется
  во всём приложении.

## §8.20 Импорт / экспорт задач (Excel)

- Меню в шапке задач: **Экспорт в Excel** (все поля: номер, название, описание,
  статус, приоритет, исполнитель, дедлайн, оценка, спринт), **Импорт из Excel**
  (создаёт задачи через API; статусы/приоритеты нормализуются, исполнитель и
  спринт мапятся по имени, неизвестные — пусто), **скачать шаблон (демо)**.
- Кнопка «?» — поповер с описанием колонок + скачивание шаблона. Всё на клиенте
  (SheetJS), импорт создаёт задачи пакетно через `POST /tasks`.

## §8.21 Аудит действий + soft-delete с восстановлением

- **Журнал действий** (`activity_log`, per-project): кто/что/когда — create / update /
  delete / restore и т.п. по всем сущностям (задачи, файлы, ресурсы, комментарии,
  спринты, участники, настройки). Хранится ВЕЧНО (важно для компаний). Страница
  «История» с поиском и фильтрами (по актору, типу сущности, действию, датам).
- **Soft-delete везде**: удаление проставляет `deletedAt` (+ `deletedById`), сущность
  скрыта, но **восстановима в течение 7 дней**. Раздел «Корзина»: список удалённого
  с кнопкой «Восстановить».
- **Крон**: окончательно удаляет всё с `deletedAt` старше 7 дней (вместе с объектами
  хранилища для файлов).

## §8.22 Умные внутренние уведомления (глобальные) + суточный email-дайджест

**Принцип: in-app уведомления — основной канал. Почта — НЕ на каждое событие
(антипаттерн), а один суточный дайджест-саммари.**

- **Глобальные, не per-project**: таблица `notifications` (userId, projectId, event,
  entityType/entityId, title, body, link, readAt). Пользователь видит уведомления
  из ВСЕХ своих проектов в одном месте.
- **Колокольчик в шапке** с баджем непрочитанных. Выпадающая панель —
  **сгруппирована по проектам**, у каждого проекта свой счётчик; клик по
  уведомлению → переход в нужный проект и к конкретной задаче/сообщению;
  «перейти в проект» — отдельным действием.
- **Прочитанность**: пометить одно / все в проекте / все; бадж пересчитывается.
- **События (всё, что касается меня)**: @упоминание (чат/задача/комментарий),
  назначение задачи на меня, смена статуса моей задачи, комментарий к моей задаче.
- **Email**: мгновенных писем НЕТ. Крон раз в сутки собирает непрочитанные
  уведомления пользователя и шлёт ОДНО письмо-саммари (сгруппировано по проектам).
  Настройка подписки = что попадает в уведомления + флаг «слать суточный дайджест».

## §8.23 Системные автосообщения в чат (события задач)

- В чат публикуются **настоящие сообщения от имени пользователя** (в обход ЛЛМ,
  без модерации) о ключевых событиях задач, со ссылкой на задачу:
  - **завершил задачу** — «Я завершил задачу TASK-42 …»
  - **назначил задачу** — «@Артём, я назначил тебе задачу TASK-42 …»
- Настройка на уровне проекта (aiConfig / projectSettings): включать ли
  автопубликацию таких сообщений (`autoPostTaskEvents`), по умолчанию включено.
- Сообщения помечаются как системные (`system=true`), рендерятся компактно
  с иконкой и кликабельной ссылкой на задачу.

## §8.24 Документы (новая сущность)

- **Документы проекта**: заголовок + богатый контент (Tiptap, тот же RichEditor).
- **Публичный доступ по ссылке**: генерируемый `publicSlug`, страница только на
  чтение без авторизации; включается/выключается владельцем.
- **Экспорт**: скачать документ (.md / .html; при возможности — .docx).
- **ЛЛМ-инструменты**: `list_documents`, `read_document` (**с чтением по частям —
  offset/limit по символам, для длинных документов**), `create_document`,
  `update_document`, `append_to_document`, `delete_document` — всё по пермишенам.
- Права по домену `documents` в общей системе пермишенов (read/write/crud).
