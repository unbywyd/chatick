# Chatick — техническое задание (живой документ)

> Концепция: [CONCEPT.md](./CONCEPT.md). Здесь — детальные требования по мере поступления.
> Обновлено: 2026-07-23.

---

## 1. Иерархия сущностей

```
Компания (Company/Team)
├── участники компании (системные роли: Admin / Manager / Member)
└── Проекты (Project = группа = чат)
    └── участники проекта (роли проекта: owner / admin / member)
```

- Компания — вне проектов, содержит множество проектов.
- Компания: **название, лого**, участники.
- Проект принадлежит компании.

## 2. Роли и пермишены

### 2.1 Системные роли компании

| Роль | Права (базовая матрица, конфигурируемая) |
|---|---|
| **Admin** | всё: настройки компании, роли, инвайты, создание/удаление проектов |
| **Manager** | создавать проекты, приглашать в проекты, приглашать в компанию |
| **Member** | участвовать в проектах, куда добавлен |

- Права заданы **логическими пермишенами** (флаги: `canCreateProjects`, `canInviteToCompany`, `canManageMembers`, …), роль = преднастроенный набор флагов. Матрица настраивается на уровне компании.
- Создавать проекты может Admin или Manager (по умолчанию).

### 2.2 Роли проекта

- owner / admin / member (как заложено в схеме).
- На уровне проекта — свои пермишены (кто может приглашать в проект, менять правила ИИ, управлять задачами и т.п.).

## 3. Приглашения

### 3.1 В компанию — с подтверждением

- Приглашение **по email** с указанием роли.
- Флоу: инвайт создан → письмо со ссылкой-токеном → приглашённый подтверждает → становится участником.
- Управление инвайтами: **переслать** (повторное письмо), **удалить/отозвать**, список pending-инвайтов.
- Если у приглашённого нет аккаунта — после Google-логина инвайт подхватывается по email.

### 3.2 В проект — без подтверждения

- Участника компании просто **включают** в проект (никакого accept-флоу).
- Постфактум отправляются письма: **«вас добавили в проект»**, **«вас убрали из проекта»**.

## 4. Правила проекта и конфигурация ИИ

Детальная страница настроек ИИ у каждого проекта.

### 4.1 Конфигурация ИИ-диспетчера (пересмотрено 2026-07-23)

Принцип: каждый параметр мапится в конкретное **действие** диспетчера, никаких абстрактных процентов.

```
aiConfig:
  mode: observer | assistant | moderator      — режим вмешательства (3 карточки)
    observer  — только перевод + ответы при прямом обращении к ИИ
    assistant — + сам отвечает на вопросы из контекста, предлагает действия (default)
    moderator — + придерживает: непонятное (уточнить), дубли (ссылка), оффтоп
  language: код языка                          — ЯЗЫК ПРОЕКТА (канонический язык чата)
  autoTranslate: bool                          — переводить сообщения на язык читателя (default on)
  answerRepeats: bool                          — дедуп: отвечать на повторные вопросы за людей (default on)
  offtopic: ignore | remind | hold             — что делать с оффтопом (default remind)
```

- «Шутки/флуд/тон» — НЕ конфиг, а текстовые правила чата (§4.2).
- Управление задачами через чат — НЕ здесь, а через пермишены участника (§4.3): ИИ выполняет
  действия с задачами только в пределах прав автора сообщения.

### 4.3 Пермишены участника проекта (задачи)

Per-user галочки на уровне участника проекта (страница «Права» в проекте):

```
permissions:
  tasks.read          — всегда true (не отключается)
  tasks.create        — создавать задачи
  tasks.edit          — редактировать задачи
  tasks.delete        — удалять задачи
  tasks.changeStatus  — менять статусы
```

- Дефолты по роли: owner/admin — всё; member — read + changeStatus.
- UI: страница с чекбоксами по каждому участнику (владелец/админ проекта редактирует).
- **Синхронизировано с чатом**: ИИ-диспетчер проверяет права автора перед действием
  («создай таску» от юзера без tasks.create → вежливый отказ).
- Расширяемо на другие домены (files.*, credentials.*) тем же механизмом.

### 4.2 Текстовые правила чата (chat rules)

- Свободное текстовое поле, описывающее правила проекта.
- **Жёсткий лимит длины — буквально пара предложений** (~300 символов): текст включается в **каждый запрос ИИ** как system-контекст, длина критична для стоимости и качества.
- Показывается каждому участнику **перед вступлением** в проект и **подтверждается** им (фиксируем факт подтверждения).
- Используется в промпте ИИ-диспетчера как правила чата.

## 5. Флоу входа (утверждено)

1. Лендинг chatick.com (Astro, en/ru/he, RTL, автодетект; пока под basic-auth) → «Начать» → app.chatick.com
2. Google OAuth → **session JWT** (личность)
3. После первого логина: **создание компании** (или принятие инвайта)
4. Выбор проекта / создание нового → обмен session на **project JWT** (личность + projectId + роль)
5. Рабочий экран (чат 40% / табы 60%)
6. Таб «О проекте» + кнопка «Сменить проект» → назад к выбору (сессия жива, без релогина в Google)

## 5.5 Пайплайн ИИ-диспетчера и Sandbox (утверждено 2026-07-23)

Отправка сообщения в группу:

1. POST → статус `pending`. Остальные видят «<Имя> пишет…», автор — «проверяется…».
   Сообщение НЕ появляется в чате ни у кого до вердикта (без скачков).
2. ИИ-диспетчер оценивает (правила чата §4.2, aiConfig §4.1, контекст переписки):
   - **PASS** → `delivered`, появляется у всех одновременно (вкл. автора).
   - **HOLD** → `held`, у автора открывается **Sandbox-оверлей**.
3. **Sandbox** — приватный временный канал автора с ИИ (никто другой его не видит):
   - исходное сообщение + замечания/вопросы ИИ;
   - диалог с ИИ до готовности; ИИ предлагает варианты сообщения;
   - годные варианты помечены ✓ и кнопкой **«Выбрать»** → уходит в общий чат, sandbox закрывается;
   - кнопка «Посмотреть чат» — подглядеть общий чат, не теряя sandbox;
   - «Отменить» — отбросить сообщение целиком;
   - обход: режим **assistant** — есть «Отправить как есть»; **moderator** — только одобренные ИИ варианты.
4. **Вложения**: файлы/картинки прикрепляются к сообщению в композере; при HOLD остаются
   привязанными и отправляются вместе с выбранным финальным вариантом.

## 5.6 Память ИИ: сжатие переписки и инструменты (утверждено 2026-07-23)

Беседы бесконечны, контекст LLM конечен, терять информацию нельзя. Трёхслойная память:

1. **Живой хвост** — последние ~30 сообщений сырыми в каждом промпте.
2. **Саммари-цепочка** — переписка нарезается на «беседы»: при накоплении >60 несжатых
   сообщений старшие 40 сжимаются ИИ в саммари с ИИ-сгенерированным **именем**
   (короткое, «о чём была беседа»), датами from/to и messageCount. Курсор —
   projects.lastSummarizedAt. В промпт идёт ОГЛАВЛЕНИЕ (список имён+дат) + последнее
   саммари целиком. Сырые сообщения не удаляются.
3. **Инструменты** — ИИ сам достаёт остальное (tool-use цикл, до 5 итераций):
   - list_summaries(page) — список бесед: имя, даты, счётчик; пагинация
   - get_summary(id) — полный текст саммари
   - search_messages(query) — поиск по сырой истории (полнота гарантирована)
   - list_files(query?) — файлы проекта (имена+ссылки), list_tasks / get_task
   - create_task / update_task / delete_task / change_task_status — CRUD задач
     **с проверкой пермишенов автора сообщения** (§4.3): нет права — вежливый отказ.

Промпт любого вызова (диспетчер, sandbox, ответы) = system + оглавление + последнее
саммари + живой хвост + tools. ИИ «видит» всю историю: свежее напрямую, старое —
через оглавление и инструменты.
